# ByteVerse 2026 — Complete Security & Architecture Audit Report

**Date:** 2026-09-01  
**Scope:** Full repository — all source files, configuration, infrastructure, and documentation  
**Auditor role:** Principal Architect · Senior Security Engineer · DevSecOps · QA Lead · Performance Engineer

---

## Executive Summary

ByteVerse 2026 is a well-conceived, feature-rich competitive programming platform. The codebase is clean, consistently structured, and clearly authored by competent developers. However, several **critical and high-severity issues** make the application **NOT production-ready in its current state**.

| Category | Rating |
|----------|--------|
| Security Posture | ⚠️ WEAK (critical hardcoded secrets, broken auth model) |
| Production Readiness | ❌ FAIL (dev bypasses reach prod, incomplete stubs) |
| Data Integrity | ⚠️ PARTIAL (race conditions, scoring inconsistencies) |
| Reliability | ⚠️ PARTIAL (single points of failure, no circuit breakers) |
| Testing | ❌ FAIL (empty e2e/load tests, critical paths untested) |
| Architecture | ✅ GOOD (clean monolith, well-separated concerns) |
| Performance | ⚠️ PARTIAL (N+1 queries, in-memory rate limits, no pagination) |

**Must-fix before deployment:** items SEC-001, SEC-002, SEC-003, SEC-004, SEC-005, REL-001, DATA-003.

## Repository Overview

- **Stack:** Next.js 15 monolith (React 19, TypeScript, Tailwind, Monaco Editor, Zustand)
- **Backend:** Next.js API Routes + NextAuth.js v5 (JWT) + Prisma 7 + PostgreSQL 16
- **Cache/Realtime:** Redis 7 (ioredis) — SSE for leaderboard, pub/sub for admin alerts
- **Code Execution:** Judge0 CE v1.13.1 (Docker, self-hosted)
- **AI:** Groq API, multi-key round-robin pool (up to 15 keys)
- **Deployment:** Docker Compose (postgres + redis + judge0 + app)

**Critical flows:**
1. Team registration (unauthenticated-friendly upsert → auto-auth credentials in response)
2. Competition round (DRAFT → ACTIVE → ENDED with SSE + polling)
3. Submission pipeline (submit → Judge0 → webhook callback → score update → leaderboard)
4. MCQ pipeline (submit → grade inline → score upsert → no webhook)
5. AI assistance (lifetime quota check → Groq call → penalty applied to round score cap)
6. Anti-cheat (client-side fullscreen/blur/key monitoring → violation POST → PIN unlock)

## Critical Findings

### SEC-001 — Hardcoded Fallback PINs in Production Unlock Endpoint
**Severity:** CRITICAL | **Confidence:** HIGH | **File:** `src/app/api/audit/violation/route.ts:82-87`

```typescript
const validPins = [
  process.env.ADMIN_PIN,
  "123456",
  "2026",
  "admin2026",
].filter(Boolean);
```

**Problem:** The `PUT /api/audit/violation` endpoint (used to unlock a locked workstation) accepts three hardcoded PINs — `123456`, `2026`, and `admin2026` — regardless of whether `ADMIN_PIN` is set. These PINs are also **printed in plain text in the client-side UI** (`AntiCheatShield.tsx:406`):

```
"The proctor will enter the Master PIN (123456 or 2026) to resume your session."
```

Any participant who reads the lock screen knows the PIN. The endpoint is unauthenticated (no session check on PUT). Any participant can call it directly from their browser console and unlock their own station.

**Attack scenario:**
```bash
curl -X PUT http://competition-server/api/audit/violation \
  -H "Content-Type: application/json" \
  -d '{"pin":"123456"}'
# → {"success":true,"message":"Station unlocked by proctor"}
```

**Fix:** Remove all hardcoded PINs. Accept only `process.env.ADMIN_PIN`. Add authentication requiring ORGANIZER role OR require the request to carry a time-limited HMAC token generated by an admin action.

### SEC-002 — Development Authorization Bypass Pattern Present Across All Admin APIs
**Severity:** CRITICAL | **Confidence:** HIGH | **Files:** Multiple

The following pattern appears in **at least 8 admin/organizer API routes**:

```typescript
const isDev = process.env.NODE_ENV !== "production";
if (!isDev) {
  if (!session?.user?.role || !requireRole("ORGANIZER", session.user.role)) {
    return NextResponse.json({ error: "Forbidden" }, { status: 403 });
  }
}
```

**Affected routes:**
- `src/app/api/admin/rounds/route.ts` (GET + POST)
- `src/app/api/admin/rounds/[id]/status/route.ts` (PATCH)
- `src/app/api/admin/rounds/[id]/problems/route.ts` (GET + POST)
- `src/app/api/admin/problems/[id]/route.ts` (DELETE + PATCH)
- `src/app/api/admin/participants/route.ts` (GET)
- `src/app/api/admin/teams/route.ts` (GET)
- `src/app/api/admin/announcements/route.ts` (POST)
- `src/app/api/admin/stats/route.ts` (GET)

**Problem:** In `development` mode (any deployment where `NODE_ENV !== "production"`), all of these endpoints skip auth entirely. If the app is deployed for staging/demo with `NODE_ENV=development` (common mistake), every endpoint is wide open. Additionally, the logic is inverted — it reads "not production means skip auth", which is the opposite of safe defaults.

**Blast radius:** Unauthenticated actors can: create/destroy rounds, publish/delete problems, read all participant data, post announcements, change round status.

**Fix:** Remove the `isDev` bypass entirely. These endpoints require auth in all environments. For local development, log in as the seeded admin.

### SEC-003 — Mass Assignment in Problem PATCH Endpoint
**Severity:** CRITICAL | **Confidence:** HIGH | **File:** `src/app/api/admin/problems/[id]/route.ts:43-48`

```typescript
const body: any = await req.json();
// ...
const problem = await db.problem.update({
  where: { id },
  data: body,  // ← raw body passed directly to Prisma
});
```

No Zod validation, no field allowlist. An attacker (or the vulnerability at SEC-002 in dev) can send arbitrary Prisma fields — including `roundId` (moving problems between rounds), `correctOption` (changing correct answers), `isPublished`, `testCases` (relation operations), etc.

**Fix:** Define a strict Zod schema of allowed PATCH fields (title, statement, constraints, sampleInput, sampleOutput, isPublished, etc.) and use `parsed.data` only.

### SEC-004 — Unauthenticated Team Join Can Create or Overwrite User Accounts
**Severity:** HIGH | **Confidence:** HIGH | **File:** `src/app/api/teams/join/route.ts:41-78`

When joining a team without a session (or when `leaderEmail` is supplied), the endpoint calls:

```typescript
const userRecord = await db.user.upsert({
  where: { email: emailToUse },
  update: { name: fullName },  // overwrites existing user's name
  create: { email, name, passwordHash, role: "PARTICIPANT" },
});
```

**Problems:**
1. If an existing user (e.g. admin) provides their email in the join form, their name is silently overwritten.
2. The auto-created account gets a weak `Math.random()`-based password (`BV-${Math.random().toString(36).slice(-8)}!`), which is cryptographically weak (not crypto.randomUUID / crypto.getRandomValues).
3. The generated password and email are returned in the API response body (`autoAuth` field) in plaintext over HTTP if TLS is not enforced. No TLS is configured in docker-compose.
4. There is no email verification — anyone can claim any email address and join a team under that identity.

**Fix:** Require authentication to join a team. Remove unauthenticated account creation from this flow. If registration-time team join is required, separate the flows and add email verification.

### SEC-005 — Judge0 Webhook Has No Auth When Secret Is Not Configured
**Severity:** HIGH | **Confidence:** HIGH | **File:** `src/app/api/judge/webhook/route.ts:7-10`

```typescript
const secret = process.env.JUDGE0_WEBHOOK_SECRET;
const authHeader = req.headers.get("authorization");
if (!secret || !authHeader || authHeader !== `Bearer ${secret}`) {
  return NextResponse.json({ error: "Unauthorized" }, { status: 401 });
}
```

When `JUDGE0_WEBHOOK_SECRET` is not set, `secret` is `undefined`, and the condition `!secret` is `true` → the request is immediately rejected. This is actually safe (deny if no secret). **However**, the Judge0 `docker/judge0.conf` does not configure a callback secret token. Judge0 sends callbacks without an Authorization header by default. This means:
- Either the webhook is permanently broken (Judge0 can never deliver results), OR
- The secret was added to `.env` but Judge0 wasn't told to send it — callbacks arrive without auth and get rejected.

**Confirmed impact:** In the provided docker-compose, `JUDGE0_WEBHOOK_SECRET` is set in the app env but `judge0.conf` has no `CALLBACKS_URL_BEARER_TOKEN`. Judge0 callbacks will be rejected → all coding submissions remain `QUEUED` forever.

**Fix:** Add `CALLBACKS_URL_BEARER_TOKEN=<same-as-JUDGE0_WEBHOOK_SECRET>` to `judge0.conf`.

### SEC-006 — Middleware Only Checks Cookie Presence, Not Validity
**Severity:** HIGH | **Confidence:** HIGH | **File:** `src/middleware.ts`

```typescript
const sessionToken =
  request.cookies.get("__Secure-authjs.session-token")?.value || ...;
if (!sessionToken) { redirect to login }
```

The middleware only checks that a session cookie **exists**. It does not validate the JWT signature, expiry, or payload. A participant could:
1. Set any cookie value (e.g. the string `"fake"`) with the name `authjs.session-token`.
2. The middleware passes them through.
3. The actual route handlers call `auth()` which validates — so they are protected **at the handler level**.

**However:** Any admin page that renders purely from server components without calling `auth()` would be accessible. Also, the middleware protects only `/admin/:path*` routes — participant routes have zero middleware protection.

**Fix:** In Next.js 15, use NextAuth's exported `auth` middleware wrapper for proper JWT validation at the edge. Replace the cookie-presence check with `export { auth as middleware } from "@/lib/auth"`.

### SEC-007 — Leaderboard SSE Endpoint Has No Authentication
**Severity:** MEDIUM | **Confidence:** HIGH | **File:** `src/app/api/leaderboard/sse/route.ts`

The SSE stream endpoint accepts any `eventId` query parameter with no session check. Anyone (unauthenticated) can subscribe to live score updates. ## Functional Findings

### FUNC-001 — Submission Scoring Is Binary (All-or-Nothing) Not Per-Test-Case
**Severity:** HIGH | **File:** `src/app/api/judge/webhook/route.ts:26-28`

```typescript
const accepted = mappedStatus === "ACCEPTED";
const testCases = submission.problem.testCases;
const passedCount = accepted ? testCases.length : 0;
const rawScore = testCases.length > 0 ? Math.round((passedCount / testCases.length) * 100) : 0;
```

If a submission passes 4/5 test cases but Judge0 returns `WRONG_ANSWER` for the batch, the participant scores 0. Judge0 CE (community edition) evaluates against a single expected output; it does not support per-test-case batch results without the batch API. The current implementation submits only once (`wait=false`) and trusts a single status. Participants who partially solve a problem get 0, which is inaccurate.

**Fix:** Use Judge0 batch submissions (one submission per test case) or accept partial credit scoring via the batch API.

### FUNC-002 — MCQ Score Does Not Apply AI Score Cap
**Severity:** HIGH | **File:** `src/app/api/mcq/submit/route.ts:84-94`

```typescript
await db.roundScore.upsert({
  where: { userId_roundId: { userId, roundId } },
  update: { rawScore: totalRoundScore, finalScore: totalRoundScore },
  // ↑ finalScore set equal to rawScore, ignoring aiScoreCap
});
```

When updating a round score from MCQ submission, `aiScoreCap` is ignored. A participant who used AI and has a cap of 75 can still have `finalScore = 100` if they correctly answer all MCQ questions after using AI.

**Fix:** Apply `Math.min(totalRoundScore, existing.aiScoreCap ?? 100)` when computing `finalScore`.

---

### FUNC-003 — AI Penalty Not Applied to Submissions After AI Is Used
**Severity:** HIGH | **File:** `src/lib/scoring.ts:156-195`

`applyAIPenalty` correctly updates `aiScoreCap` on `RoundScore`. However, `updateRoundScore` (called from the Judge0 webhook) reads `existing?.aiScoreCap ?? 100` at the time of judging. If a participant:
1. Submits code (queued)
2. Uses AI assistance (penalty applied, cap set to 75)
3. Submission is judged (reads current `aiScoreCap = 75`) ✅

This ordering is correct. **However**, in the reverse order:
1. Uses AI (cap = 75, creates RoundScore with finalScore=0, cap=75)
2. Makes a new submission after AI
3. `updateRoundScore` reads `existing.aiScoreCap = 75` ✅

**Edge case found:** If AI is used and the RoundScore does not yet exist (first AI use, no submission yet), `applyAIPenalty` creates RoundScore with `rawScore: 0`. When the submission is later judged, the upsert updates `rawScore` and applies the cap correctly. **This works.** However, there is a race condition: if judge webhook fires before AI penalty is committed (concurrent requests), `aiScoreCap` could be read as 100.

### FUNC-004 — Team Delete Leaves Members as Orphaned Participants
**Severity:** MEDIUM | **File:** `src/app/api/teams/route.ts:169-195`

When a leader calls `DELETE /api/teams`, the team is deleted via `db.team.delete`. The schema has `onDelete: Cascade` on `TeamMember`, so members are removed. However, the `TeamMember` for the leader is also cascade-deleted, making the leader free to re-register. **A non-leader member who left before deletion cannot re-join** because their `TeamMember` might still exist from a previous team. This flow is inconsistent with the DISQUALIFIED-status check in team registration.

## Performance Findings

### PERF-001 — N+1 Queries in Team Score Calculation
**Severity:** HIGH | **File:** `src/lib/scoring.ts:5-106`

`calculateTeamScore` is called once per user submission judged. It runs:
1. `db.team.findUnique` (includes members + their roundScores)
2. `db.teamScore.upsert`
3. `db.round.findUnique` (to get eventId)
4. `redisClient.del` × 2
5. `redisClient.publish`

This is acceptable in isolation, but it is called from within a `db.$transaction` in the webhook handler. A database query inside a transaction that calls out to Redis can cause transaction timeouts and connection pool exhaustion under load.

---

### PERF-002 — In-Memory Compile Run Tracker Is Not Shared Across Processes
**Severity:** HIGH | **File:** `src/app/api/submissions/run/route.ts:28`

```typescript
const compileTracker = new Map<string, number>();
```

This `Map` is module-level — it is only in-memory for the current Node.js process. In any scaled or even Docker-restarted deployment, the counter resets. Participants can bypass the 10-run limit by refreshing the server or in a multi-instance deployment.

**Fix:** Move the counter to Redis: `INCR compile:${userId}:${problemId}` with `EXPIRE` set to round duration.

---

### PERF-003 — SSE Connections Create a New Redis Connection Per Client
**Severity:** HIGH | **File:** `src/lib/redis.ts:36-39`

```typescript
subscribe: (channel: string, handler: (msg: string) => void) => {
  const sub = new Redis(process.env.REDIS_URL!);  // new connection per call
  sub.subscribe(channel);
  // ...
}
```

Every SSE subscriber (leaderboard, round stream) opens a **new dedicated Redis connection**. With 100 participants each subscribing to leaderboard + round stream, that is 200+ Redis connections. Redis default max connections is 10,000, but this is wasteful and creates connection overhead.

**Fix:** Use a shared Redis subscriber instance with a multiplexed channel handler map.

The participants endpoint returns all participants with full nested data (aiUsages, submissions count, auditLogs, teamMember, team, roundScores, disqualification) in a single query. With 200+ participants this is a large payload and a slow query.

## Reliability Findings

### REL-001 — No Database Migration Step in Deployment
**Severity:** CRITICAL | **File:** `Dockerfile`, `package.json`

The `CMD ["node", "server.js"]` in the Dockerfile starts the app directly without running `prisma migrate deploy`. If the schema has changed since the last deployment, the app will start against a stale database schema, causing Prisma errors or data corruption.

The `docker-compose.yml` has no migration service/hook. `db:migrate` is a manual script only.

**Fix:** Add a migration entrypoint:
```dockerfile
CMD ["sh", "-c", "npx prisma migrate deploy && node server.js"]
```
Or use a separate init container.

---

### REL-002 — Judge0 Uses the Same Postgres and Redis as the App
**Severity:** HIGH | **File:** `docker/judge0.conf`

Judge0 is configured to share the app's Redis instance (`REDIS_URL=redis://redis:6379`). However, Judge0 uses its own Postgres database (`judge0`/`judge0pass`). The issue is that the docker-compose `judge0` service does not have its own Postgres — it `depends_on` the shared `postgres` container. **Judge0 will create its own schema in the shared `byteverse` Postgres instance**, or fail if not configured correctly. The credentials in `judge0.conf` (`judge0`/`judge0pass`) do not match the shared Postgres credentials (`byteverse`/`${POSTGRES_PASSWORD}`).

**Fix:** Either give Judge0 its own Postgres service, or configure `judge0.conf` with the correct credentials and database name.

---

### REL-003 — Redis Failure Silently Allows Rate Limit Bypass
**Severity:** HIGH | **File:** `src/lib/redis.ts:41-43`

```typescript
incr: async (key: string) => {
  try { return await getRedis().incr(key); } catch { return Infinity; }
},
```

On Redis failure, `incr` returns `Infinity`. In `checkRateLimit`:

```typescript
const count = await redisClient.incr(`rl:${key}`);
if (!Number.isFinite(count)) { return true; }  // allow on Infinity
```

On Redis failure, all rate limits are bypassed (allow-all). While this prevents service disruption, it means during a Redis outage the auth registration endpoint, AI endpoint, and all other rate-limited endpoints become unthrottled.

**Fix:** Return a configured constant (e.g., `limit + 1`) to enforce limits on Redis failure, or log and block during extended Redis downtime.

---

### REL-004 — No Timeout on Prisma Queries
**Severity:** MEDIUM | **File:** `src/lib/db.ts`

No query timeout is configured on the Prisma client. A slow or deadlocked database query will hold a Next.js serverless function/worker indefinitely, eventually exhausting the connection pool.

---

### REL-005 — No Health Checks for App Service in Docker Compose
**Severity:** MEDIUM | **File:** `docker-compose.yml`

Postgres and Redis have health checks. The `app` service and `judge0` service do not. `depends_on: condition: service_healthy` for postgres/redis is correct, but app readiness is never verified.

---

### REL-006 — SSE Stream Does Not Handle Redis Disconnection
**Severity:** MEDIUM | **File:** `src/app/api/leaderboard/sse/route.ts`

If Redis disconnects after an SSE stream is established, the subscription silently dies. The client receives no error, the heartbeat keeps the connection alive, but no score updates are delivered. Clients have no way to know the stream is broken.

## Infrastructure Findings

### INF-001 — Judge0 Runs as `privileged: true` with Shared Postgres
**Severity:** HIGH | **File:** `docker-compose.yml:38`

Judge0 requires `privileged: true` for sandbox isolation (cgroups, namespaces). Running with host-level privileges on the same Docker network as the app and database is a significant attack surface. A Judge0 vulnerability could allow container escape to the host and access to other containers.

**Recommendation:** Run Judge0 on a separate host/VM in a DMZ, connected only via its API. Never co-locate it with the database on the same `privileged` Docker network.

---

### INF-002 — Default `changeme` Passwords in docker-compose
**Severity:** HIGH | **File:** `docker-compose.yml:8,22`

```yaml
POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-changeme}
REDIS_PASSWORD: ${REDIS_PASSWORD:-changeme}
```

If deployed without setting environment variables, default passwords are `changeme`. The ports 5433 (Postgres) and 6379 (Redis) are exposed to the host network, meaning anyone on the local network can connect with these default credentials.

**Fix:** Remove the `:-changeme` fallback; fail fast if the env var is not set.

---

### INF-003 — Redis Port 6379 Exposed to Host in docker-compose
**Severity:** MEDIUM | **File:** `docker-compose.yml:25`

Redis is exposed on `0.0.0.0:6379` of the host. Even with a password, this expands the attack surface. Redis should only be accessible from within the Docker network.

**Fix:** Remove the `ports` mapping for Redis (and Postgres) unless external access is required.

---

### INF-004 — No TLS/HTTPS Configuration
**Severity:** HIGH | **Confidence:** HIGH

No TLS termination is configured anywhere in the Docker Compose stack. The app serves HTTP on port 3000. The `autoAuth` credentials (plaintext email + password) returned in team join/create responses are transmitted over plaintext HTTP.

**Fix:** Add a reverse proxy (nginx/Traefik) with TLS termination in front of the app.

---

### INF-005 — CI Build Does Not Run Database Migrations
**Severity:** MEDIUM | **File:** `.github/workflows/ci.yml`

The CI test job starts a Postgres container but never runs `prisma migrate deploy` or `prisma db push`. Tests that touch the database would fail. The `-- --passWithNoTests` flag hides this because no integration tests are run.

## Edge Cases

1. **Round extended beyond midnight** — no handling for day boundary in timer display
2. **User submits after round ends** — `if (round?.status !== "ACTIVE" && process.env.NODE_ENV === "production")` allows submissions in development; also, if a submission is queued just before round end and judged after, the score is still recorded
3. **Empty `AI_API_KEYS`** — `getNextHealthyKey` throws; there is a check `if (RAW_KEYS.length === 0)` but the error message leaks internal config details
4. **Team with 1 member** — `calculateTeamScore` correctly handles this via `TREAT_AS_ZERO` policy, but team score display shows `memberScoresSum / t.members.length` (wrong divisor for 1-member teams when `TREAT_AS_ZERO` divides by 2)
5. **Concurrent team creation with same name** — Prisma unique constraint on `Team.name` will throw P2002; this is handled but the error code check is string-based `e.code === "P2002"` — correct
6. **Judge0 down** — `submitToJudge` throws; caught and returns 503; submission is never created — idempotency key is consumed on retry attempt? No — the submission is not created on Judge0 failure, so the idempotency key is not stored, and a retry with a new key works. Correct.
7. **All Groq keys in cooldown** — `getNextHealthyKey` falls back to the key with earliest expiry; the API call may still fail and the user gets a 429. Acceptable.
8. **MCQ `correctOption` is null** — `problem.correctOption?.toUpperCase() === selectedOption.toUpperCase()` → `undefined === "A"` → false → score 0. A problem with no correct option set will always score 0 — silent data bug.
